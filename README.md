# Knowledge Hub

HWP·PPT·스캔 PDF 등 포맷이 섞이고 파일명 규칙이 없는 R&D 중소기업 환경에서, 신입이 선배 없이도 내용 기반으로 문서를 검색하는 로컬(폐쇄망) 도구다.

아산 AX 글로벌 인재양성 프로그램(블루문드림, 2026.05.23 ~ 2026.07.25) 약 10주 동안 3조가 만든 프로젝트다. R&D 문서를 많이 다루는 외국계 기업 코싸이온을 고객사로 두고 진행했다. 7월 25일 IR Day에서 발표했고, 프로그램이 끝난 뒤 7월 31일까지 구조 정리 작업을 이어 갔다.

드라이브에 `최종_진짜최종_v2` 같은 파일이 열 개씩 쌓여 있으면 신입사원은 폐기된 버전으로 일을 시작하게 된다. 담당자가 회사를 떠나면 그 문서를 찾는 경로도 같이 끊긴다. 파일 이름이나 폴더 위치를 몰라도 "이런 내용이 있던 문서"로 찾을 수 있게 하는 게 목표였다.

고객사는 외부와 끊긴 폐쇄망에서 이 도구를 상업 용도로 쓴다. 그래서 외부 클라우드 API 없이 CPU만으로 돌아가야 했고, 오픈소스는 상업적 이용이 가능한 라이선스만 쓸 수 있었다. 프로그램 기간에는 팀 테스트와 시연을 위해 Railway 클라우드에 올려 두었고, 사내 설치는 온프레미스로 옮기는 것을 전제로 했다.

> 이 저장소는 팀 저장소 [`Buroong-Junseo/km-platform`](https://github.com/Buroong-Junseo/km-platform)에서 시작했다. 2026년 7월 30일 팀원과 합의해 개인 저장소로 옮겼고, 팀 저장소의 커밋 이력(브랜치 14개)은 모두 이 저장소에 들어 있다. AX 프로그램이 끝난 뒤에는 이 저장소에서 서버와 배포 구성을 바꿔 가며 개발을 이어 가고 있다.

## 주요 기능

- PDF·DOCX·PPTX·XLSX·HWP·HWPX·TXT·MD를 올리면 백그라운드에서 파싱해 표와 스캔 페이지(한국어 OCR)까지 텍스트로 뽑고, 페이지 단위로 저장한다. 파일 하나에 최대 500MB, PDF는 3,000쪽까지 받는다.
- 검색은 파일명 검색이 기본이고, 유사 검색으로 바꾸면 내용으로 찾는다. 질문과 뜻이 가까운 페이지를 찾아 원본 파일의 몇 쪽인지까지 보여주고, 한국어로 물어도 영어 문서를 찾는다.
- Google 계정으로 로그인한다. 문서는 업로드한 사람의 부서를 따라가서 같은 부서만 볼 수 있고, 관리자가 문서별로 예외를 줄 수 있다.
- 관리자 화면에서 문서·계정·부서·카테고리를 관리한다. 파싱에 실패했거나 OCR 품질이 낮은 문서는 "확인 필요 문서" 탭에 모이고, 문서를 지우면 누가 왜 지웠는지 "삭제 보고서"에 남는다. 업로드·검색 통계도 여기서 본다.
- 북마크, 문서 댓글, 알림이 있다. 같은 파일명을 다시 올리면 덮어쓰지 않고 새 버전으로 추가하며, DB와 파일은 자동으로 백업한다.

HWP 지원에 대해: 본 제품은 한글과컴퓨터의 한글 문서 파일(.hwp) 공개 문서를 참고하여 개발하였습니다.

## 팀과 역할

3조는 4명이었다.

| 이름 | 맡은 부분 |
|---|---|
| 송승현 (팀장 · 조장 · 검수) | HWP 처리 + 마크다운 후처리, 클라이언트 컨택, 오픈소스 라이선스 검토. 이후 로그인·권한·관리자 등 2차 기능, 프론트엔드 대부분, 검색 재설계, Elasticsearch·Docling 전환 |
| 윤준서 | PDF 파싱(pdfplumber·camelot·EasyOCR). 이후 백엔드 통합과 첫 Railway 배포, 배포 환경 안정화 |
| 김태훈 | 임베딩 + 하이브리드 검색엔진(BM25 + 벡터) |
| 김기빈 | 백엔드(FastAPI, 업로드 처리)와 화면(React) 초기 구현 |

전체 136개 커밋 중 74개가 내 커밋이다.

### 협업 방식

네 명이 한 저장소에서 동시에 작업하다 보니 서로의 코드를 덮어쓰지 않는 게 제일 중요했다. 그래서 팀장으로서 규칙을 몇 가지 정했다.

- 저장소 최상위에 역할 이름으로 폴더를 나눴다(`parser/`, `hwp_postprocess/`, `search/`, `backend/`). 각자 자기 역할 브랜치(`feature/parser`, `feature/hwp`, `feature/search`, `feature/backend`)를 쓰고, 그 안에서도 자기 폴더 안에서만 작업했다.
- PR을 올리기 전에는 단톡방에 먼저 공지했다. 무엇을 바꿨는지, 다른 사람 코드에 영향이 있는지 미리 알리려는 것이었다. PR 검수는 내가 맡았다.
- `main`에 직접 푸시해야 할 때는 회의를 한 번 열어 변경 내용을 설명한 뒤에 푸시했다.

이 규칙은 팀 저장소를 쓰던 때의 것이다. 개인 저장소로 옮긴 뒤로는 혼자 작업하고 있어서 브랜치를 `main`, `backend`, `frontend` 세 개로 줄였다.

## 내가 한 일

시간 순서대로 적는다. 원인을 자세히 추적한 내용은 `docs/오류보고서/`와 [`UI_UPDATES_2026-07-24.md`](UI_UPDATES_2026-07-24.md)에 따로 남겨 두었다.

### 1. HWP 처리 + 마크다운 후처리

역할을 나눌 때 멘토님이 이 파트가 제일 까다로울 것 같다고 하셨는데, 그 말을 듣고 오히려 해 보고 싶어져서 맡았다. 고객사 문서 상당수가 한글(HWP) 파일이고, HWP는 공개된 형식이 아니라서 내용을 꺼내는 것부터가 일이었다.

이 파트는 `hwp_postprocess` 패키지로 만들었다. 확장자를 보고 알맞은 파서로 보내는 디스패처를 두고, 형식마다 다른 방법으로 내용을 읽은 뒤 결과를 모두 같은 Markdown 형태로 맞췄다. 그래야 검색 쪽에서 원본 형식을 신경 쓰지 않고 똑같이 다룰 수 있었다.

| 형식 | 처리 방법 |
|---|---|
| HWP | LibreOffice(headless)로 DOCX로 바꾼 뒤 DOCX 파서로 넘김 |
| HWPX | 압축 파일 안의 `section*.xml`을 직접 열어 단락과 표를 읽음 |
| DOCX | 제목 스타일을 Markdown 제목 단계(`#`, `##`)로, 표를 Markdown 표로 변환. 문서에 박힌 이미지는 EasyOCR로 글자를 읽음 |
| XLSX / XLS | 시트마다 Markdown 표 하나로 변환 |
| PPTX / PPT | LibreOffice로 PDF로 바꾼 뒤 윤준서 님의 PDF 파이프라인에 연결 |

HWP를 읽는 파이썬 라이브러리로는 pyhwp가 가장 잘 알려져 있었지만 AGPL-3.0이라 쓰지 않았다. 네트워크로 서비스하면 소스 전체를 공개해야 하는 조건이 있어서 상업용 사내 도구에는 맞지 않았다. 대신 LibreOffice를 별도 프로세스로 호출하는 방식 하나로 통일했다.

나중에 배포 서버에서 HWP 업로드가 계속 실패했다. 처음엔 한글 파일명 인코딩 문제로 의심했는데 아니었고, 리눅스용 LibreOffice에는 HWP 가져오기 필터가 아예 없었다. H2Orestart 확장과 `libreoffice-java-common`을 설치해서 해결했다. 같은 시기에 구형 `.xls`는 LibreOffice가 "성공"으로 끝나면서도 결과 파일을 만들지 않는 문제가 있어서, xlrd로 직접 읽도록 바꿨다.

7월 28일 파서를 Docling 하나로 합치면서 이 패키지는 정리했다(6번 참고). Docling이 HWP를 지원하지 않아서 HWP·HWPX 새 업로드도 이때 막았다. 코드는 git 이력에 남아 있다.

### 2. 클라이언트 컨택

고객사 연구자님과 연락하는 일을 맡았다. 매주 진행보고서를 써서 구글 드라이브에 올리고, 이메일로 보고드린 뒤 피드백을 받았다. 받은 피드백 가운데 설계에 반영한 것은 이런 것들이다.

- 목표로 잡은 "검색 정확도 80%"가 무슨 뜻이냐는 질문을 받고, "검색 결과 상위 5개 안에 원하는 문서가 들어오는 비율"로 정의를 고쳤다.
- 시스템이 최신 문서를 자동으로 골라 확정된 것처럼 보여주면 안 된다는 의견에 따라, 후보로만 제안하고 대표 문서는 사용자가 직접 지정하게 바꿨다.
- 연구자님이 제안한 문서 분류(사양서·연구자료·발표자료·보고서)를 카테고리로 그대로 썼다.
- 인터뷰에서 "GPU가 없다"는 말을 직접 들었고, CPU만으로 돌아가게 만든 이유가 이것이다.

### 3. 모델 호환성과 오픈소스 라이선스 검토

고객사는 폐쇄망에서 상업 용도로 이 도구를 쓴다. 기능이 되는지와는 따로, 이 라이브러리와 모델을 그 환경에서 써도 되는지 확인하는 일을 맡았다.

기준은 인터넷 없이 동작할 것, GPU 없이 CPU로 돌아갈 것, 상업적 이용이 자유로운 라이선스(Apache 2.0, MIT 등)일 것, 이렇게 세 가지였다. 이 기준 때문에 빠지거나 바뀐 것들이 있다.

- pyhwp는 AGPL-3.0이라 채택하지 않고 LibreOffice 방식으로 대신했다.
- PyMuPDF도 AGPL-3.0이었다. 초기 PDF 파서에 들어 있었는데 같은 이유로 pdfplumber로 교체됐다(교체 작업은 윤준서 님).
- Ghostscript도 AGPL이라, 표 추출 백엔드 후보였지만 7월 2일에 아예 빼기로 했다.
- LibreOffice와 ClamAV처럼 GPL·MPL 계열인 도구는 코드에 라이브러리로 붙이지 않고 별도 프로세스로 호출만 했다.
- 임베딩 모델은 다국어 MiniLM(Apache 2.0)으로 정했다. 한국어로 물어서 영어 문서를 찾아야 했고, 384차원이라 CPU에서도 빨라서 폐쇄망 서버에서 돌리기 좋았다.

`requirements.txt`에 라이브러리마다 라이선스를 주석으로 달아 둔 것도 이때 한 일이다.

### 4. 로그인과 2차 기능 (7월 20일~21일)

MVP를 배포한 뒤, 사내에서 쓰려면 필요한 기능을 한꺼번에 붙였다. Google 로그인, 관리자와 일반 사용자 화면 분리, 북마크, 알림, 계정별 검색 기록, 부서별 문서 열람 제한이 이때 들어갔다. 태블릿·모바일 폭에서 화면이 깨지는 문제도 같이 고쳤다.

AI 요약과 자동 분류(Ollama + Qwen2.5)도 이때 넣었다가 하루 만에 뺐다. 배포 서버에는 Ollama를 올리지 않은 상태였고, 그걸 위해 서버 비용을 늘릴 만큼 쓸모가 크지 않다고 봤다. 검색 결과에서 원본 페이지를 바로 열어 볼 수 있어서 요약이 없어도 쓰는 데 지장이 없었다.

로그인을 켠 날 장애가 한 번 났다. 배포 서버에 Google 클라이언트 ID를 넣자마자 사이트가 빈 화면이 됐다. 인증 미들웨어가 `/`만 공개 경로로 두고 있어서, 로그인 화면을 그려야 할 JS·CSS 파일까지 401로 막고 있었다. 로컬에서는 프론트(5173)와 백엔드(8000)를 따로 띄우니 문제가 안 보였고, 백엔드가 정적 파일까지 서빙하는 배포 환경에서만 생겼다. `/assets/` 경로를 공개 목록에 넣어서 고쳤고, 서비스가 멈춘 상태라 이때만 `main`에 바로 반영했다.

### 5. 관리자 화면, 운영 기능, 검색 재설계 (7월 22일~25일)

관리자 화면은 직접 써 보면서 계속 고쳤다. 통계를 제목 옆에 요약해서 보여주고, 파싱 실패 문서와 OCR 확인이 필요한 문서를 한 탭에 모았다. 카테고리를 지우기 전에는 그 안의 문서를 다른 카테고리로 옮기게 했고, 문서를 지울 때 사유를 남기는 "삭제 보고서"를 만들었다.

운영 쪽으로는 DB와 업로드 파일을 매일 자동 백업하고(최근 14개 보관), 업로드하자마자 미러 사본을 두고, 삭제된 파일은 3일 뒤에 정리하게 했다. 요청이 한꺼번에 몰리는 걸 막는 요청 수 제한과 `robots.txt`도 이때 넣었다.

검색 방식도 이때 바꿨다. 원래는 "정확도/균형/의미" 3단계로 BM25와 벡터 점수를 섞었는데, "지식관리"를 검색하면 형태소 분석 때문에 "지식"만 들어간 엉뚱한 문서가 섞여 나왔다. 그래서 검색을 두 가지로 나눴다. 파일명 검색은 파일명 부분 일치로 찾아 최신순으로 보여준다. 유사 검색은 임베딩 유사도로 먼저 후보를 뽑고, BM25는 그 후보 안에서 순위만 조정한다(RRF 결합). BM25가 후보를 새로 끌어오지 못하니 엉뚱한 문서가 끼어들 수 없다.

이 기간에 고친 문제 몇 가지를 더 적는다.

- 일반 사용자 화면이 로그인을 붙이기 전 코드 그대로 관리자 전용 API를 부르고 있어서 일반 계정에서 403이 났다. 관리자 API를 열어 주지 않고, 부서 권한을 지키는 일반용 API를 따로 만들었다.
- 같은 파일명을 다시 올리면 덮어쓰게 돼 있었는데, 사내 문서는 버전이 다르면 둘 다 남아야 해서 새 버전으로 추가하게 바꿨다. 이걸 고치다가 저장 경로가 겹쳐 기존 파일 내용이 덮어써질 수 있는 문제도 찾아서 막았다.
- 화면이 8초, 20초마다 서버에 상태를 묻는 폴링이 있었다. 사용자가 늘면 서버 부하도 같이 늘어나서, 수동 새로고침과 창으로 돌아왔을 때만 확인하는 방식으로 바꿨다.
- 배포 DB(PostgreSQL)에서만 날짜 필터가 서버 오류를 내던 문제와, 모든 시각이 9시간 늦게 찍히던 문제를 고쳤다.
- 업로드 파일 악성코드 검사(ClamAV)를 붙였다가 같은 날 되돌렸다. ClamAV 데몬이 시그니처 DB만으로 메모리를 800MB~1.2GB 쓰면서 OCR·임베딩 모델과 메모리를 다퉜다. 스와핑 때문에 PostgreSQL 체크포인트 쓰기가 269초까지 걸리고 일부 업로드가 500 오류로 실패해서, 당시 서버로는 무리였다.

### 6. Elasticsearch·Docling으로 구조 전환 (7월 28일~31일)

프로그램이 끝난 뒤에 한 작업이다. 기존에는 벡터 인덱스(turbovec)를 메모리에 두고, BM25 인덱스는 검색할 때마다 새로 만들고, 둘을 합치는 RRF 공식도 직접 짜 넣었다. 이걸 Elasticsearch 하나로 옮겼다.

- BM25 검색과 벡터 kNN 검색을 Elasticsearch에 따로 질의하고, 두 결과를 합치는 RRF는 파이썬에서 직접 계산한다(벡터 k=30, BM25 k=60). Elasticsearch에도 RRF 기능이 있지만 무료 자체 호스팅 버전에서는 Enterprise 라이선스가 필요해서 쓸 수 없었다.
- 한국어 형태소 분석기 nori를 붙였다. 플러그인만 설치해서는 안 되고, 인덱스 설정에서 분석기를 직접 정의해야 했다.
- 배포 환경에서는 권한 문제로 Elasticsearch에 영구 저장소를 붙일 수 없었다. 그래서 Elasticsearch가 재시작돼서 비면, DB에 남겨 둔 임베딩으로 다시 색인하는 작업이 10분마다 돌게 했다.
- PDF·DOCX·PPTX·XLSX 파서를 Docling 하나로 합쳤다. LibreOffice·pdfplumber·camelot 등이 나눠 하던 일을 한 곳으로 모았고, OCR 품질이 낮은 페이지는 Docling이 매기는 등급(POOR/FAIR)으로 판단한다. 대신 HWP·HWPX 업로드는 포기했다. 이미 올라간 HWP 문서는 계속 볼 수 있다.

같은 시기에 저장소를 개인 저장소로 옮기고, 서비스 이름과 도메인에서 `km-platform`을 지우고, 사내 배포용으로 화면 톤을 맞추고, 화면마다 URL이 따로 잡히게 바꿨다.

## 로컬에서 실행하기

2026년 10월 Windows 11에서 처음부터 다시 띄워 보면서 확인한 순서다. Python 3.12, Node.js, Docker Desktop이 필요하다.

**1. 환경 변수**

`backend/.env`를 만든다. 이 파일은 git에 올라가지 않는다.

```
GOOGLE_CLIENT_ID=<Google OAuth 클라이언트 ID>   # 비워 두면 로그인 없이 동작한다
SESSION_SECRET=<임의의 긴 문자열>
ADMIN_EMAILS=<관리자 이메일, 쉼표로 구분>
```

**2. OpenSearch**

nori 플러그인을 넣은 이미지를 빌드해서 띄운다. 보안 플러그인을 끈 로컬 전용 설정이라 포트는 이 PC(127.0.0.1)에만 열린다.

```bash
cd backend/opensearch
docker compose up -d --build
```

**3. 백엔드**

```bash
cd backend
python -m venv .venv
.venv/Scripts/python -m pip install -r requirements.txt --extra-index-url https://download.pytorch.org/whl/cpu
PYTHONUTF8=1 HF_HUB_DISABLE_SYMLINKS=1 .venv/Scripts/python -m uvicorn main:app --port 8000
```

Windows에서는 `HF_HUB_DISABLE_SYMLINKS=1`이 없으면 Docling 모델을 받을 때 권한 오류가 난다. 처음 실행할 때 파싱 모델과 임베딩 모델(KURE-v1, 약 2.3GB)을 내려받느라 시간이 걸린다. 임베딩 모델은 서버가 뜬 직후 백그라운드에서 미리 올린다.

**4. 프론트엔드**

```bash
cd frontend
npm ci
VITE_API_URL=http://localhost:8000 npx vite --port 5173
```

브라우저에서 `http://localhost:5173`으로 연다. Google 로그인을 쓰려면 Google Cloud Console의 OAuth 클라이언트에 `http://localhost:5173`이 승인된 JavaScript 원본으로 등록돼 있어야 한다.

기존 문서를 검색 인덱스에 다시 넣어야 할 때는 `backend/`에서 `python scripts/search_backfill.py`를 실행한다. 임베딩 모델을 바꿨다면 `--reembed`를 붙여 벡터부터 다시 만든다(이때 `EMBED_MODEL`, `EMBED_DIM` 환경변수를 새 모델에 맞추고 `OPENSEARCH_INDEX`도 새 이름으로 준다).

배포용 단일 이미지 빌드 방법은 [`DEPLOY.md`](DEPLOY.md)에 있다.

### 2026년 10월 24~25일: 라이선스 정리, HWP 재지원, 모델 결정

처음 정한 라이선스 기준(상업적 이용이 자유로운 허용형 오픈소스만)을 최우선으로 두고 다시 정리했다.

- **검색 엔진**: Elasticsearch 8.15 배포판의 라이선스가 Elastic License 2.0이라(이미지 안 `LICENSE.txt`로 확인) 기준에 맞지 않았다. OpenSearch 3.9.0(Apache-2.0)과 nori 플러그인(Apache-2.0)으로 바꿨다. 검색 방식(BM25와 벡터를 따로 찾아 파이썬에서 RRF로 합치는 구조)은 그대로다.
- **OCR**: EasyOCR가 끌어오는 python-bidi가 LGPL이었다. Docling이 지원하는 RapidOCR(Apache-2.0)로 바꾸고 한국어 인식 모델을 지정했다. 이전 설정은 한국어를 전혀 읽지 못했는데(스캔본 한국어 재현율 0%), 지금은 59.5%를 읽는다.
- **HWP·HWPX**: 한컴이 공개한 「한글 문서 파일 형식 5.0」 명세를 보고 `core/hwp_parser.py`에 직접 구현했다. 외부 프로그램이나 GPL 계열 확장 없이 파이썬(olefile, lxml)만 쓴다. 이 PC에 있던 HWP·HWPX 35개를 모두 읽었고, 같은 문서를 한컴이 내보낸 PDF와 대조했을 때 본문 글자의 97.8%가 일치했다(빠진 부분은 쪽 번호와 반복 머리말). HWP는 쪽이 파일에 고정돼 있지 않아 DOCX처럼 쪽 번호를 따로 보여주지 않는다.
- **임베딩 모델**: 아래 측정에서 가장 높게 나온 KURE-v1(MIT)로 바꿨다.

라이선스 점검 결과 지금 백엔드 패키지 142개 중 허용형이 아닌 것은 certifi와 tqdm(둘 다 MPL-2.0)뿐이다. 둘 다 requests·huggingface_hub 같은 필수 라이브러리가 요구해서 뺄 수 없다. 수정하지 않고 쓰는 경우 MPL-2.0은 상업적 이용을 막지 않는다.

### 검색 품질 측정

`eval/run_eval.py`로 실제 API에 문서 23개(PDF, 스캔 PDF, DOCX, PPTX, XLSX, HWP, HWPX, MD, TXT)를 올리고, 질문 47개를 유사 검색으로 돌려 정답 문서가 몇 위에 나오는지 쟀다. 측정용 문서와 질문은 팀원·학교 문서가 섞여 있어서 저장소에 올리지 않았다.

| 구성 | 1위 적중 | 5위 안 적중 | MRR |
|---|---|---|---|
| 정리 전 (Elasticsearch + MiniLM) | 27.7% | 51.1% | 0.366 |
| 정리 후 + MiniLM | 61.7% | 93.6% | 0.721 |
| 정리 후 + multilingual-e5-small | 78.7% | 93.6% | 0.859 |
| 정리 후 + multilingual-e5-base | 74.5% | 97.9% | 0.840 |
| 정리 후 + bge-m3 | 85.1% | 100% | 0.915 |
| **정리 후 + KURE-v1 (현재)** | **89.4%** | **100%** | **0.941** |

"5위 안 적중"이 PRD 목표 지표(상위 5개 안에 원하는 문서가 들어오는 비율 80%)다. 정리 전 51.1%의 원인은 측정하면서 찾았다. HWP를 받지 못했고, 스캔본 한국어를 읽지 못했고, 일부 PDF는 Docling이 글자를 깨뜨려 읽는 바람에 문서 전체가 "확인 필요"로 빠져 검색 대상이 아니었다. 셋 다 고쳤다.

KURE-v1의 대가는 속도다. 이 노트북 CPU에서 청크 1,512개를 임베딩하는 데 MiniLM은 42초, KURE-v1은 471초가 걸렸다. 검색 한 번은 평균 0.18초다. 더 가벼운 구성이 필요하면 `EMBED_MODEL=intfloat/multilingual-e5-small`, `EMBED_DIM=384`로 바꾸면 된다.

질문은 문서를 읽고 직접 만들었기 때문에 실제 사용자 질문보다 쉬울 수 있다. 같은 질문으로 구성만 바꿔 비교하는 용도로 봐야 한다.

| DB | PostgreSQL(배포), SQLite(로컬) | `DATABASE_URL`이 있으면 PostgreSQL, 없으면 SQLite를 써서 코드를 고치지 않고 환경만 바꿔 옮길 수 있다 |
| 문서 파싱 | Docling(레이아웃·표 인식) + RapidOCR 한국어 모델, HWP·HWPX는 자체 파서 | 여러 형식을 외부 프로그램 없이 처리한다. HWP는 Docling이 지원하지 않아 한컴 공개 명세로 직접 구현했다 |
| 검색 | OpenSearch 3.9 + nori, BM25 + 벡터 kNN, RRF는 파이썬에서 직접 결합 | Apache-2.0이라 라이선스 기준에 맞고, 키워드 검색과 의미 검색을 같이 쓸 수 있다 |
| 임베딩 | `nlpai-lab/KURE-v1` (1024차원, MIT) | 측정한 6개 모델 중 정답 1위 비율이 가장 높았다(89.4%). 한국어 질문으로 영어 문서도 찾는다 |
| 인증 | Google OAuth ID 토큰 검증 + 서명된 세션 쿠키 | 클라이언트 시크릿 없이 ID 토큰 검증만으로 로그인을 붙일 수 있었다 |
| 배포(AX 기간) | Docker 단일 이미지, Railway | 프론트 빌드 결과를 백엔드가 같이 서빙해서 서비스 하나로 운영했다 |

문서를 올리면 Docling(HWP·HWPX는 자체 파서)이 페이지 단위 텍스트로 바꾸고, 400자 단위 조각마다 KURE-v1이 1024차원 벡터를 만든다. 이 벡터는 텍스트와 함께 DB에 저장되고 OpenSearch에 색인된다. 검색할 때는 같은 질문으로 BM25 검색과 벡터 검색을 따로 돌려 RRF로 순위를 합치고, 부서 권한으로 한 번 더 거른 뒤 원본 파일의 해당 페이지와 함께 돌려준다. 이 과정 전체가 GPU와 외부 API 없이 CPU만으로 돌아간다.
