# Knowledge Hub

HWP·PPT·스캔 PDF 등 포맷이 섞이고 파일명 규칙이 없는 R&D 중소기업 환경에서, **신입이 선배 없이도 내용 기반으로 문서를 검색**하는 로컬(폐쇄망) 도구다.

아산 AX 글로벌 인재양성 프로그램(블루문드림, 2026.05.23 – 2026.07.25) 약 10주 동안 3조가 만든 프로젝트로, R&D 문서가 핵심 자산인 외국계 기업 코싸이온을 고객사로 두고 진행했다. 7월 25일 IR Day에서 발표했고, 프로그램이 끝난 뒤 7월 31일까지 구조 정리 작업을 이어 갔다.

출발점은 단순했다. 드라이브에 `최종_진짜최종_v2` 같은 파일이 열 개씩 쌓여 있으면 신입사원은 폐기된 버전으로 일을 시작하게 되고, 담당자가 회사를 떠나면 그 문서를 찾는 경로도 같이 끊긴다. 그래서 파일 이름이나 폴더 위치를 몰라도 "이런 내용이 있던 문서"로 찾을 수 있게 하는 것을 목표로 삼았다.

실제 고객사 환경은 외부와 끊긴 폐쇄망이고, 상업 용도로 쓰는 사내 도구다. 그래서 외부 클라우드 API 없이 CPU만으로 돌아가야 했고, 쓰는 오픈소스는 전부 상업적 이용이 가능한 라이선스여야 했다. 프로그램 기간에는 팀 테스트와 시연을 위해 Railway 클라우드에 올려 두었고, 실제 사내 설치는 온프레미스 이전을 전제로 했다.

> 이 저장소는 팀 저장소 [`Buroong-Junseo/km-platform`](https://github.com/Buroong-Junseo/km-platform)에서 시작했다. 2026년 7월 30일 팀원과 합의해 개인 저장소로 옮겼고, 팀 저장소의 커밋 이력(브랜치 14개)은 빠짐없이 이 저장소에 들어 있다. AX 프로그램이 끝난 뒤에는 이 저장소에서 서버와 배포 구조를 바꿔 가며 이어서 개발하고 있다.

## 주요 기능

- **업로드와 파싱**: PDF·DOCX·PPTX·XLSX·TXT·MD를 받는다. 업로드하면 파싱이 백그라운드에서 돌고, 표와 스캔 페이지(OCR)까지 텍스트로 뽑아 페이지 단위로 저장한다. 파일 하나에 최대 500MB, PDF는 3,000쪽까지 받는다.
- **검색 두 가지**: 기본은 파일명 검색이다. "유사 검색"으로 바꾸면 내용으로 찾는데, 질문과 뜻이 가까운 페이지를 찾아 원본 파일의 몇 쪽인지까지 보여준다. 한국어로 물어도 영어 문서를 찾는다.
- **권한**: Google 계정으로 로그인하고, 문서는 업로드한 사람의 부서를 따라간다. 같은 부서만 볼 수 있고, 관리자가 문서별로 예외 허용을 줄 수 있다.
- **관리자 화면**: 문서·계정·부서·카테고리 관리, 파싱 실패나 OCR 품질이 낮은 페이지를 모아 보는 "확인 필요 문서", 누가 왜 지웠는지 남기는 "삭제 보고서", 업로드·검색 통계.
- **협업과 운영**: 북마크, 문서 댓글, 알림, 같은 파일명을 다시 올리면 덮어쓰지 않고 새 버전으로 추가, DB와 파일 자동 백업.

## 팀과 역할

3조는 4명이었다.

| 이름 | 맡은 부분 |
|---|---|
| **송승현** (팀장 · 조장 · 검수) | HWP 처리 + 마크다운 후처리, 클라이언트 컨택, 오픈소스 라이선스 검토. 이후 로그인·권한·관리자 등 2차 기능, 프론트엔드 대부분, 검색 재설계, Elasticsearch·Docling 전환 |
| 윤준서 | PDF 파싱(pdfplumber·camelot·EasyOCR). 이후 백엔드 통합과 첫 Railway 배포·배포 환경 안정화 |
| 김태훈 | 임베딩 + 하이브리드 검색엔진(BM25 + 벡터) |
| 김기빈 | 백엔드(FastAPI, 업로드 처리)와 화면(React) 초기 구현 |

전체 136개 커밋 중 74개가 내 커밋이다.

### 협업 방식

네 명이 한 저장소에서 동시에 작업하다 보니 서로의 코드를 덮어쓰지 않는 게 가장 중요했다. 그래서 팀장으로서 몇 가지 규칙을 정해 운영했다.

- 저장소 최상위에 역할 이름으로 폴더를 나눴다(`parser/`, `hwp_postprocess/`, `search/`, `backend/`). 각자 자기 역할 브랜치(`feature/parser`, `feature/hwp`, `feature/search`, `feature/backend`)를 쓰고, 그 안에서도 자기 역할 폴더 안에서만 작업했다.
- 작업을 합칠 때는 PR을 올리기 전에 단톡방에 먼저 공지했다. 무엇을 바꿨고 다른 사람 코드에 영향이 있는지 미리 알리기 위해서였다. PR 검수는 내가 맡았다.
- `main`에 직접 푸시해야 하는 상황이 생기면 그냥 올리지 않고, 회의를 한 번 열어 변경 내용을 설명한 뒤에 푸시했다.

이 규칙은 팀 저장소 시절 기준이다. 개인 저장소로 옮긴 뒤로는 혼자 작업하고 있어서 브랜치를 `main`·`backend`·`frontend` 세 개로 단순화했다.

### 1. HWP 처리 + 마크다운 후처리

역할을 나눌 때 멘토님이 이 파트가 제일 까다로울 것 같다고 하셨는데, 그 말을 듣고 오히려 해 보고 싶어져서 맡았다. 고객사 문서 상당수가 한글(HWP) 파일인데, HWP는 공개된 형식이 아니라서 내용을 꺼내는 것부터가 일이었다.

결과물은 `hwp_postprocess` 패키지였다. 확장자를 보고 알맞은 파서로 보내는 디스패처를 두고, 형식마다 다른 방법으로 내용을 읽은 뒤 **전부 같은 Markdown 형태로 맞추는 후처리**를 했다. 검색 쪽에서는 원본이 무슨 형식이었는지 신경 쓰지 않고 똑같이 다룰 수 있게 하려는 목적이었다.

| 형식 | 처리 방법 |
|---|---|
| HWP | LibreOffice(headless)로 DOCX로 바꾼 뒤 DOCX 파서로 넘김 |
| HWPX | 압축 파일 안의 `section*.xml`을 직접 열어 단락과 표를 읽음 |
| DOCX | 제목 스타일을 Markdown 제목 단계(`#`, `##`)로, 표를 Markdown 표로 변환. 문서에 박힌 이미지는 EasyOCR로 글자를 읽음 |
| XLSX / XLS | 시트마다 Markdown 표 하나로 변환 |
| PPTX / PPT | LibreOffice로 PDF로 바꾼 뒤 윤준서 님의 PDF 파이프라인에 연결 |

HWP를 읽는 파이썬 라이브러리로는 pyhwp가 가장 잘 알려져 있었지만 AGPL-3.0이라 쓰지 않았다. 네트워크로 서비스하면 전체 소스를 공개해야 하는 조건이 있어서, 상업용 사내 도구에는 맞지 않았다. 대신 LibreOffice를 별도 프로세스로 호출하는 경로 하나로 통일했다.

나중에 배포 서버에서 HWP 업로드가 계속 실패하는 문제가 생겼다. 처음엔 한글 파일명 인코딩 문제로 의심했지만 아니었고, 리눅스용 LibreOffice에 HWP 가져오기 필터가 아예 없다는 걸 확인했다. H2Orestart 확장과 `libreoffice-java-common`을 설치해서 해결했다. 같은 시기에 구형 `.xls`가 LibreOffice에서 "성공"으로 끝나는데 결과 파일이 없는 조용한 실패를 일으켜서, xlrd로 직접 읽도록 바꿨다.

7월 28일 파서 전체를 Docling으로 통합하면서 이 패키지는 정리됐다(6번 항목). Docling이 HWP를 지원하지 않아서 HWP·HWPX 새 업로드는 이때 막았다. 코드는 git 이력에 그대로 남아 있다.

### 2. 클라이언트 컨택

고객사 연구자님과의 소통 창구를 맡았다. 매주 진행보고서를 써서 구글 드라이브에 올리고, 이메일로 보고드린 뒤 피드백을 받는 방식으로 진행했다. 실제로 설계에 반영한 피드백 중 몇 가지:

- 목표로 잡은 "검색 정확도 80%"가 무슨 뜻이냐는 지적을 받고, "검색 결과 상위 5개 안에 원하는 문서가 들어오는 비율"로 정의를 명확히 했다.
- 시스템이 최신 문서를 자동으로 판별해 확정처럼 보여주면 안 된다는 의견에 따라, 시스템은 후보로만 제안하고 사용자가 직접 대표 문서를 지정하는 구조로 바꿨다.
- 연구자님이 제안한 문서 분류 체계(사양서·연구자료·발표자료·보고서)를 카테고리로 그대로 채택했다.
- 인터뷰에서 "GPU가 없다"는 제약을 직접 확인했고, 이게 CPU만으로 돌아가는 구성을 택한 근거가 됐다.

### 3. 모델 호환성과 오픈소스 라이선스 검토

고객사는 폐쇄망에서 상업 용도로 이 도구를 쓴다. 그래서 기능이 되는지와 별개로, "이 라이브러리와 모델을 그 환경에서 써도 되는가"를 따로 검토하는 역할을 맡았다.

기준은 세 가지였다. 인터넷 없이 동작할 것, GPU 없이 CPU로 돌아갈 것, 상업적 이용이 자유로운 라이선스(Apache 2.0, MIT 등)일 것. 이 기준으로 걸러낸 사례들:

- **pyhwp (AGPL-3.0)**: 채택하지 않고 LibreOffice 경로로 대체했다.
- **PyMuPDF (AGPL-3.0)**: 초기 PDF 파서에 들어 있었는데, 같은 기준에 걸려 pdfplumber로 교체됐다(교체 작업은 윤준서 님).
- **Ghostscript (AGPL)**: 표 추출 백엔드 후보였지만 7월 2일에 전면 제외로 확정했다.
- **LibreOffice, ClamAV처럼 GPL·MPL 계열 도구**: 코드에 라이브러리로 붙이지 않고 별도 프로세스로 호출만 하는 방식으로 썼다.
- **임베딩 모델**: 다국어 MiniLM(Apache 2.0)을 골랐다. 한국어 질문으로 영어 문서를 찾아야 했고, CPU에서도 빠른 384차원 모델이라 폐쇄망 서버에서 돌리기에 맞았다.

`requirements.txt`에 라이브러리마다 라이선스를 주석으로 적어 둔 것도 이 검토의 흔적이다.

### 4. 로그인과 2차 기능 (7월 20일~21일)

MVP가 배포된 뒤 실제 사내에서 쓰려면 필요한 기능을 한 번에 붙였다. Google 로그인, 관리자와 일반 사용자 화면 분리, 북마크, 알림, 계정별 검색 기록, 부서별 문서 열람 제한이 이때 들어갔다. 태블릿·모바일 폭에서 화면이 깨지는 문제도 같이 손봤다.

AI 요약과 자동 분류(Ollama + Qwen2.5)도 이때 넣었는데, 하루 만에 뺐다. 배포 서버에는 Ollama를 올리지 않은 상태였고, 그걸 위해 서버 비용을 늘리기에는 효용이 낮다고 판단했다. 검색 결과에서 원본 페이지를 바로 열어 확인하는 구조라 요약이 없어도 쓰는 데 지장이 없었다.

로그인을 켠 날에는 장애도 한 번 겪었다. 배포 서버에 Google 클라이언트 ID를 넣는 순간 사이트가 빈 화면이 됐다. 인증 미들웨어가 `/`만 공개 경로로 두고 있어서, 로그인 화면을 그려야 할 JS·CSS 파일까지 401로 막고 있었다. 로컬에서는 프론트(5173)와 백엔드(8000)를 따로 띄우니 드러나지 않았고, 정적 파일을 백엔드가 함께 서빙하는 배포 환경에서만 터졌다. `/assets/` 경로를 공개 목록에 추가해서 고쳤다. 서비스가 멈춘 상태라 이때는 예외적으로 `main`에 바로 반영했다.

### 5. 관리자 화면, 운영 기능, 검색 재설계 (7월 22일~25일)

관리자 화면을 실제로 써 보면서 계속 다듬었다. 통계를 제목 옆에 요약하고, 파싱 실패 문서와 OCR 확인이 필요한 문서를 한 탭에 모으고, 카테고리를 지우기 전에 문서를 다른 카테고리로 옮기게 하고, 문서 삭제 시 사유를 남기는 "삭제 보고서"를 만들었다.

운영 쪽으로는 DB와 업로드 파일을 매일 자동 백업하고(최근 14개 보관), 업로드 즉시 미러 사본을 두고, 삭제된 파일은 3일 유예 뒤에 정리하도록 했다. 과도한 요청을 막는 요청 수 제한과 `robots.txt`도 이때 넣었다.

검색은 이 시기에 구조를 바꿨다. 원래는 "정확도/균형/의미" 3단계로 BM25와 벡터 점수를 섞는 방식이었는데, 형태소 분석 특성상 "지식관리"를 검색하면 "지식"만 들어간 엉뚱한 문서가 섞여 들어왔다. 그래서 둘로 나눴다.

- **파일명 검색**: 파일명 부분 일치, 최신순.
- **유사 검색**: 먼저 임베딩 유사도로 후보를 뽑고, BM25는 그 후보 안에서 순위만 조정한다(RRF 결합). BM25가 새 후보를 끌어오지 못하게 해서 엉뚱한 문서가 끼어드는 걸 구조적으로 막았다.

이 기간에 찾아서 고친 문제 중 기억에 남는 것들:

- 일반 사용자 화면이 로그인 도입 전 코드 그대로 관리자 전용 API를 부르고 있어서 일반 계정에서 403이 났다. 관리자 API를 열어 주는 대신, 부서 권한을 지키는 일반용 API를 따로 만들었다.
- 같은 파일명을 다시 올리면 "덮어쓰기"를 하게 돼 있었는데, 사내 문서는 버전이 다르면 둘 다 남아야 한다고 보고 "새 버전 추가" 방식으로 바꿨다. 이 과정에서 저장 경로가 겹쳐 기존 파일 내용이 실제로 덮어써질 수 있는 문제도 미리 찾아 막았다.
- 화면이 8초·20초마다 서버에 상태를 물어보는 폴링이 있었는데, 사용자가 늘수록 서버 부하가 같이 늘어나는 구조라 수동 새로고침과 창 포커스 시 확인으로 바꿨다.
- 배포 DB(PostgreSQL)에서만 날짜 필터가 서버 오류를 내던 문제, 모든 시각이 9시간 늦게 표시되던 문제를 고쳤다.
- 업로드 파일 악성코드 검사(ClamAV)를 붙였다가 같은 날 되돌렸다. ClamAV 데몬이 시그니처 DB만으로 메모리를 800MB~1.2GB 쓰면서 OCR·임베딩 모델과 메모리를 다퉜고, 스와핑 때문에 PostgreSQL 체크포인트 쓰기가 269초까지 걸리고 일부 업로드가 500 오류로 실패했다. 당시 서버 자원으로는 감당이 안 됐다.

### 6. Elasticsearch·Docling으로 구조 전환 (7월 28일~31일)

프로그램이 끝난 뒤 가장 큰 작업이었다. 기존 구조는 벡터 인덱스(turbovec)를 메모리에 두고, BM25 인덱스는 검색할 때마다 새로 만들고, 둘을 합치는 RRF 공식도 직접 짜 넣은 형태였다. 이걸 Elasticsearch 하나로 옮겼다.

- BM25 검색과 벡터 kNN 검색을 각각 Elasticsearch에 질의하고, 두 결과를 합치는 RRF는 파이썬에서 직접 계산한다(벡터 k=30, BM25 k=60). Elasticsearch에도 RRF 기능이 있지만 무료 자체 호스팅 버전에서는 Enterprise 라이선스가 필요해서 쓸 수 없었다.
- 한국어 형태소 분석기 nori를 연결했다. nori는 플러그인만 설치해서는 안 되고, 인덱스 설정에서 분석기를 직접 정의해야 했다.
- 배포 환경에서는 권한 문제로 Elasticsearch에 영구 저장소를 붙일 수 없었다. 그래서 Elasticsearch가 재시작으로 비워지면, DB에 원본으로 남겨 둔 임베딩으로 자동 재색인하는 작업을 10분 주기로 돌게 했다.
- 파서는 PDF·DOCX·PPTX·XLSX 전부 Docling 하나로 통합했다. LibreOffice·pdfplumber·camelot 등 여러 라이브러리가 하던 일을 한 곳으로 모았고, OCR 품질이 낮은 페이지는 Docling이 매기는 등급(POOR/FAIR)으로 판단한다. 대신 HWP·HWPX 업로드는 포기했다. 이미 올라간 HWP 문서는 계속 열람할 수 있다.

같은 시기에 저장소를 개인 저장소로 옮기고, 서비스 이름과 도메인에서 `km-platform` 표기를 정리하고, 사내 배포용으로 화면 톤을 맞추고 화면마다 URL이 따로 잡히도록 바꿨다.

## 로컬에서 실행하기

2026년 10월 Windows 11에서 처음부터 다시 띄워 보며 확인한 순서다. Python 3.12, Node.js, Docker Desktop이 필요하다.

**1. 환경 변수** — `backend/.env`를 만든다(git에 올라가지 않는다).

```
GOOGLE_CLIENT_ID=<Google OAuth 클라이언트 ID>   # 비워 두면 로그인 없이 동작한다
SESSION_SECRET=<임의의 긴 문자열>
ADMIN_EMAILS=<관리자 이메일, 쉼표로 구분>
```

**2. Elasticsearch** — 코드가 nori 분석기를 쓰기 때문에 nori가 들어간 이미지를 빌드해서 띄운다. `backend/elasticsearch/docker-compose.yml`은 nori가 없는 기본 이미지를 쓰고 있어서 지금 코드와 맞지 않는다.

```bash
cd backend/elasticsearch
docker build -t knowledge-hub-es-nori:8.15.0 .
docker run -d --name project_knowledge_hub_es -p 9200:9200 \
  -e discovery.type=single-node -e xpack.security.enabled=false \
  -e "ES_JAVA_OPTS=-Xms1g -Xmx1g" \
  -v project_knowledge_hub_es_data:/usr/share/elasticsearch/data \
  knowledge-hub-es-nori:8.15.0
```

**3. 백엔드**

```bash
cd backend
python -m venv .venv
.venv/Scripts/python -m pip install -r requirements.txt --extra-index-url https://download.pytorch.org/whl/cpu
PYTHONUTF8=1 HF_HUB_DISABLE_SYMLINKS=1 .venv/Scripts/python -m uvicorn main:app --port 8000
```

Windows에서는 `HF_HUB_DISABLE_SYMLINKS=1`이 없으면 Docling 모델을 받을 때 권한 오류가 난다. 첫 업로드 때 파싱·임베딩 모델을 내려받느라 몇 분 걸린다.

**4. 프론트엔드**

```bash
cd frontend
npm ci
VITE_API_URL=http://localhost:8000 npx vite --port 5173
```

브라우저에서 `http://localhost:5173`으로 연다. Google 로그인을 쓰려면 Google Cloud Console의 OAuth 클라이언트에 `http://localhost:5173`이 승인된 JavaScript 원본으로 등록돼 있어야 한다.

기존 문서를 Elasticsearch에 다시 넣어야 할 때는 `backend/`에서 `python scripts/es_backfill.py`를 실행한다.

배포용 단일 이미지 빌드는 [`DEPLOY.md`](DEPLOY.md)에 정리돼 있다.

## 처음 계획한 기술 스택과 바뀐 과정

프로젝트를 시작할 때 팀이 정한 기술 스택은 아래와 같았다.

- 파싱: PyMuPDF + EasyOCR(PDF) / pyhwp + LibreOffice(HWP)
- 검색: BM25(rank-bm25 + kiwipiepy) + 벡터(MiniLM) 하이브리드 — Vector DB 미정
- 백엔드/화면: FastAPI + SQLite / React
- 요약(보조): Ollama + Gemma 3 4B (프로토타입 포함 여부 미정)
- 전부 CPU 전용, 외부 클라우드 API 미사용(폐쇄망 전제)
- 오픈소스는 상업적 이용 가능 라이선스(MIT/Apache 2.0)만 사용

만들면서 부딪힌 문제에 따라 대부분이 바뀌었다. 지금 코드 기준으로 정리하면 이렇다.

## 기술 요약

| 구분 | 사용한 것 | 고른 이유 |
|---|---|---|
| 백엔드 | FastAPI, Uvicorn, SQLAlchemy(async) | 대용량 업로드를 받으면서 파싱을 백그라운드로 돌리기 위해 비동기 구조를 택했다 |
| 프론트엔드 | React 19, Vite, Ant Design, TanStack Query, Axios | 검색·업로드·관리자·내 정보 화면. 서버 상태는 TanStack Query로 관리한다 |
| DB | PostgreSQL(배포), SQLite(로컬) | `DATABASE_URL` 유무로 자동 전환해서, 코드 수정 없이 환경만 바꿔 옮길 수 있게 했다 |
| 문서 파싱 | Docling(레이아웃·표 인식) + EasyOCR | 여러 형식을 한 파이프라인으로 처리하고, 외부 시스템 프로그램 없이 동작한다 |
| 검색 | Elasticsearch 8.15 + nori, BM25 + 벡터 kNN, RRF는 파이썬에서 직접 결합 | 키워드와 의미 검색을 같이 쓰되, 무료 버전에서 막힌 RRF 기능을 피했다 |
| 임베딩 | `paraphrase-multilingual-MiniLM-L12-v2` (384차원) | 한국어 질문으로 영어 문서를 찾을 수 있고 CPU에서도 빠르다 |
| 인증 | Google OAuth ID 토큰 검증 + 서명된 세션 쿠키 | 비밀키 없이 ID 토큰 검증만으로 로그인을 붙일 수 있었다 |
| 배포(AX 기간) | Docker 단일 이미지, Railway | 프론트 빌드 결과를 백엔드가 같이 서빙해서 서비스 하나로 운영했다 |

정리하면, 업로드된 문서는 Docling이 페이지 단위 텍스트로 바꾸고, MiniLM이 각 페이지를 384차원 벡터로 만들어 원본과 함께 DB에 저장한 뒤 Elasticsearch에 색인한다. 검색할 때는 같은 질문으로 BM25 검색과 벡터 검색을 따로 돌려 RRF로 순위를 합치고, 부서 권한으로 한 번 더 걸러서 원본 파일의 해당 페이지와 함께 돌려준다. 전 과정이 GPU와 외부 API 없이 CPU만으로 돌아간다.
