## 프로젝트 개요

본 프로젝트는 아산 AX 글로벌 인재양성 프로그램(블루문드림, 2026.05.23 ~ 2026.07.25)의 기업 연계 과제로 개발했습니다. R&D 문서를 많이 다루는 외국계 기업 코싸이온을 고객사로 두고 진행했고, 7월 25일 IR Day에서 발표했습니다. 프로그램이 끝난 뒤에도 이 저장소에서 개발을 이어 가고 있습니다.

### 팀 구성 및 역할

4인 팀으로 진행했으며, 본인은 **팀장(조장)** 을 맡아 다음을 담당했습니다.

- HWP 처리와 마크다운 후처리 (이후 한컴 공개 명세로 HWP 파서를 직접 구현)
- 고객사 연구자님과의 주간 보고와 피드백 반영
- 오픈소스 라이선스·모델 검토 (폐쇄망·상업 이용 기준)
- 로그인·권한·관리자 화면 등 2차 기능과 프론트엔드 대부분
- 검색 구조 재설계 (Elasticsearch → OpenSearch 전환, 임베딩 모델 선정, 무관 결과 거르기)
- PR 검수와 팀 저장소 규칙 관리

## 📌 프로젝트 소개

드라이브에 `최종_진짜최종_v2` 같은 파일이 열 개씩 쌓여 있으면 신입사원은 폐기된 버전으로 일을 시작하게 됩니다. 담당자가 회사를 떠나면 그 문서를 찾는 경로도 같이 끊깁니다. 고객사는 HWP·PPT·스캔 PDF가 섞여 있고 파일명 규칙도 없는 환경이었습니다.

문서를 올리면 내용을 페이지 단위로 읽어 두고, 검색하면 질문과 뜻이 가까운 페이지를 원본 파일의 몇 쪽인지까지 보여줍니다. 고객사가 외부와 끊긴 폐쇄망에서 상업 용도로 쓰기 때문에, GPU와 외부 API 없이 CPU만으로 동작하고 상업적 이용이 가능한 라이선스만 사용했습니다.

## 🏗️ 시스템 아키텍처

```
브라우저 (사용자 · 관리자)
        │  HTTPS
        ▼
     Caddy  ──►  FastAPI 백엔드 (React 빌드 결과도 함께 서빙)
                      │
     ┌────────────────┼──────────────────┬─────────────────────┐
     ▼                ▼                  ▼                     ▼
 PostgreSQL     OpenSearch 3.9      KURE-v1 임베딩       문서 파싱
 (문서·계정·    (BM25 + nori,       (1024차원, CPU)      Docling + RapidOCR 한국어,
  삭제 기록)     벡터 kNN)                               HWP·HWPX 자체 파서
```

**설계에서 지킨 세 가지**

1. **외부 API 없이 CPU만으로 동작합니다.** 고객사 인터뷰에서 GPU가 없다는 말을 직접 들었습니다. 파싱, OCR, 임베딩, 검색이 모두 서버 한 대 안에서 돌고, 모델 파일도 이미지 안에 들어 있어서 폐쇄망으로 그대로 옮길 수 있습니다.
2. **상업적 이용이 자유로운 라이선스만 씁니다.** 이 기준 때문에 pyhwp·PyMuPDF(AGPL), Elasticsearch(Elastic License 2.0), python-bidi(LGPL)를 빼거나 바꿨습니다. HWP는 쓸 수 있는 라이브러리가 없어서 한컴 공개 명세를 보고 파서를 직접 짰습니다.
3. **키워드 검색과 의미 검색을 따로 돌려 합칩니다.** 같은 질문으로 BM25 검색과 벡터 검색을 각각 돌려 RRF로 순위를 합칩니다. 의미 검색은 아무리 먼 문서라도 점수를 매겨 돌려주기 때문에, 키워드 일치 비율과 의미 점수 기준으로 관련 없는 문서를 거릅니다.

| 분류 | 기술 |
|---|---|
| Frontend | React 19, Vite, Ant Design, TanStack Query, Axios |
| Backend | FastAPI, Uvicorn, SQLAlchemy(async). `DATABASE_URL`이 있으면 PostgreSQL, 없으면 SQLite |
| 문서 파싱 | Docling(레이아웃·표 인식) + RapidOCR 한국어 모델, HWP·HWPX는 자체 파서(olefile, lxml) |
| 검색 | OpenSearch 3.9 + nori, BM25 + 벡터 kNN, RRF는 파이썬에서 직접 결합 |
| 임베딩 | `nlpai-lab/KURE-v1` (1024차원, MIT) |
| 인증 | Google OAuth ID 토큰 검증 + 서명된 세션 쿠키 |
| 실행 환경 | Docker Compose(Caddy + 앱 + OpenSearch + Postgres 17), Ubuntu Server 26.04 |

## ✨ 주요 기능

### 사용자
- PDF·DOCX·PPTX·XLSX·HWP·HWPX·TXT·MD 업로드. 백그라운드에서 표와 스캔 페이지(한국어 OCR)까지 텍스트로 뽑습니다. 파일 하나에 최대 500MB, PDF는 3,000쪽까지 받습니다.
- 파일명 검색과 유사 검색. 유사 검색은 내용으로 찾고, 원본 파일의 해당 쪽을 바로 열 수 있습니다. 한국어로 물어도 영어 문서를 찾습니다.
- 같은 파일명을 다시 올리면 덮어쓰지 않고 새 버전으로 추가합니다.
- 북마크, 문서 댓글, 댓글 알림. 알림을 누르면 해당 문서와 댓글로 바로 이동합니다.
- 문서마다 다운로드 횟수를 보여줍니다. 실제로 파일을 받을 때만 올라갑니다.
- Google 계정으로 로그인하고, 같은 부서 문서만 볼 수 있습니다.

### 관리자
- 문서·계정·부서·카테고리 관리, 업로드·검색 통계
- 확인 필요 문서: 파싱에 실패했거나 OCR 품질이 낮은 문서를 한 탭에 모읍니다.
- 삭제 보고서와 휴지통: 관리자가 지운 문서와 본인이 지운 문서 모두 누가, 언제, 왜 지웠는지 남습니다. 30일 안에는 원래 문서 번호 그대로 복원되고 댓글·북마크도 함께 돌아오며, 30일이 지나면 파일과 DB 기록을 완전히 지웁니다.
- 문서별 열람 권한 예외 지정
- DB와 업로드 파일 매일 자동 백업(최근 14개 보관)

HWP 지원에 대해: 본 제품은 한글과컴퓨터의 한글 문서 파일(.hwp) 공개 문서를 참고하여 개발하였습니다.

## 📐 검색 품질 측정

`eval/run_eval.py`로 실제 API에 문서 23개(PDF, 스캔 PDF, DOCX, PPTX, XLSX, HWP, HWPX, MD, TXT)를 올리고, 질문 47개를 유사 검색으로 돌려 정답 문서가 몇 위에 나오는지 쟀습니다. 측정용 문서에 팀원·학교 문서가 섞여 있어서 문서와 질문은 저장소에 올리지 않았습니다.

| 구성 | 1위 적중 | 5위 안 적중 | MRR |
|---|---|---|---|
| 정리 전 (Elasticsearch + MiniLM) | 27.7% | 51.1% | 0.366 |
| 정리 후 + MiniLM | 61.7% | 93.6% | 0.721 |
| 정리 후 + multilingual-e5-small | 78.7% | 93.6% | 0.859 |
| 정리 후 + multilingual-e5-base | 74.5% | 97.9% | 0.840 |
| 정리 후 + bge-m3 | 85.1% | 100% | 0.915 |
| **정리 후 + KURE-v1 (현재)** | **89.4%** | **100%** | **0.941** |

- "5위 안 적중"이 고객사와 정한 목표 지표(상위 5개 안에 원하는 문서가 들어오는 비율 80%)입니다.
- 정리 전 수치가 낮았던 원인은 HWP를 받지 못한 것, 스캔본 한국어를 읽지 못한 것(재현율 0%), 일부 PDF가 깨져 검색 대상에서 빠진 것이었습니다. 셋 다 고쳤고, 스캔본 한국어 재현율은 지금 59.5%입니다.
- KURE-v1은 느립니다. 16스레드 CPU에서 청크 1,512개를 임베딩하는 데 MiniLM은 42초, KURE-v1은 471초가 걸렸습니다. 검색 한 번은 평균 0.18초입니다.

문서와 상관없는 질문 30개(예: "김치찌개 끓이는 법", "주말 날씨 어때")로 무관 결과 거르기도 쟀습니다.

| | 거르기 전 | 거른 후 |
|---|---|---|
| 정답 1위 / 5위 안 / MRR | 89.4% / 100% / 0.941 | 89.4% / 100% / 0.941 |
| 무관 질문 평균 결과 수 | 11.7개 (최대 22개) | 1.0개 (최대 4개) |
| 결과가 0건인 무관 질문 | 0 / 30 | 16 / 30 |

질문은 문서를 읽고 직접 만들었기 때문에 실제 사용자 질문보다 쉬울 수 있습니다. 같은 질문으로 구성만 바꿔 비교하는 용도로 봐야 합니다.

## 🚀 로컬 실행 방법

Python 3.12, Node.js, Docker Desktop이 필요합니다. 2026년 10월 Windows 11에서 처음부터 다시 띄워 보며 확인한 순서입니다.

### 환경 변수
`backend/.env`를 만듭니다. 이 파일은 git에 올라가지 않습니다.
```
GOOGLE_CLIENT_ID=<Google OAuth 클라이언트 ID>   # 비워 두면 로그인 없이 동작
SESSION_SECRET=<임의의 긴 문자열>
ADMIN_EMAILS=<관리자 이메일, 쉼표로 구분>
```

### OpenSearch
```bash
cd backend/opensearch
docker compose up -d --build
```
nori 플러그인을 넣은 이미지입니다. 보안 플러그인을 끈 로컬 전용 설정이라 포트는 127.0.0.1에만 열립니다.

### 백엔드
```bash
cd backend
python -m venv .venv
.venv/Scripts/python -m pip install -r requirements.txt -c requirements.lock --extra-index-url https://download.pytorch.org/whl/cpu
PYTHONUTF8=1 HF_HUB_DISABLE_SYMLINKS=1 .venv/Scripts/python -m uvicorn main:app --port 8000
```

### 프론트엔드
```bash
cd frontend
npm ci
VITE_API_URL=http://localhost:8000 npx vite --port 5173
```

- Windows에서는 `HF_HUB_DISABLE_SYMLINKS=1`이 없으면 Docling 모델을 받을 때 권한 오류가 납니다.
- 처음 실행할 때 파싱 모델과 임베딩 모델(KURE-v1, 약 2.3GB)을 내려받느라 시간이 걸립니다.
- Google 로그인을 쓰려면 OAuth 클라이언트에 `http://localhost:5173`을 승인된 JavaScript 원본으로 등록해야 합니다.
- 검색 인덱스를 다시 채울 때는 `backend/`에서 `python scripts/search_backfill.py`를 실행합니다. 임베딩 모델을 바꿨다면 `--reembed`를 붙입니다.
- 더 가벼운 임베딩이 필요하면 `EMBED_MODEL=intfloat/multilingual-e5-small`, `EMBED_DIM=384`로 바꿉니다.
- 운영 서버 구성은 [DEPLOY.md](DEPLOY.md)에 있습니다.

### 폴더 구조
```
backend/
  main.py              API, 업로드·파싱·검색 흐름, 백그라운드 작업(백업, 휴지통 정리, 인덱스 복구)
  core/                문서 파싱 (docling_parser.py, hwp_parser.py, parser.py, office_adapter.py)
  search/              OpenSearch 색인·하이브리드 검색, 임베딩 모델
  opensearch/          nori를 넣은 OpenSearch 이미지와 로컬용 docker-compose.yml
  scripts/             검색 인덱스 재색인(search_backfill.py)
eval/run_eval.py       검색 품질 측정
deploy/                운영 서버용 docker-compose, Caddyfile, 서버 준비 스크립트
frontend/src/          검색·업로드·관리자·내 정보 화면
parser/                초기 PDF 파서 원본 (팀원 작업 보존용, 지금은 쓰지 않음)
docs/                  작업 기록, 오류 보고서, 기획 문서
ir-deck/               IR Day 발표 자료
```

## 📋 브랜치 전략

```
main                  ← 배포 기준 브랜치
├── backend           ← 백엔드 작업
└── frontend          ← 프론트엔드 작업
```

개인 저장소로 옮긴 뒤에는 혼자 작업해서 세 개로 줄였습니다. 팀 저장소를 쓰던 때는 아래와 같았습니다.

```
main
├── feature/parser    (윤준서 — PDF 파싱)
├── feature/hwp       (송승현 — HWP 처리·후처리)
├── feature/search    (김태훈 — 임베딩·하이브리드 검색)
└── feature/backend   (김기빈 — 백엔드·화면)
```

네 명이 한 저장소에서 동시에 작업하면서 서로의 코드를 덮어쓰지 않도록 다음 규칙을 정했습니다.

- 저장소 최상위를 역할별 폴더로 나누고, 각자 자기 브랜치와 자기 폴더 안에서만 작업했습니다.
- PR을 올리기 전에 단톡방에 무엇을 바꿨는지, 다른 사람 코드에 영향이 있는지 먼저 알렸습니다. PR 검수는 제가 맡았습니다.
- `main`에 직접 푸시해야 할 때는 회의에서 변경 내용을 설명한 뒤에 푸시했습니다.
