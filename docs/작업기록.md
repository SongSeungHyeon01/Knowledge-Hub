## AX 프로그램 기간 (2026.05 ~ 2026.07)

### 1. HWP 처리와 마크다운 후처리

역할을 나눌 때 멘토님이 이 파트가 제일 까다로울 것 같다고 하셨고, 그 말을 듣고 해 보고 싶어서 맡았습니다. 고객사 문서 상당수가 한글(HWP) 파일인데, 당시에는 HWP에서 내용을 꺼내는 것부터 쉽지 않았습니다.

`hwp_postprocess` 패키지로 만들었습니다. 확장자를 보고 알맞은 파서로 보내고, 형식마다 다른 방법으로 읽은 결과를 모두 같은 Markdown 형태로 맞췄습니다. 검색 쪽에서 원본 형식을 따지지 않고 똑같이 다루게 하려는 것이었습니다.

| 형식 | 처리 방법 |
|---|---|
| HWP | LibreOffice(headless)로 DOCX로 바꾼 뒤 DOCX 파서로 넘김 |
| HWPX | 압축 파일 안의 `section*.xml`을 직접 열어 단락과 표를 읽음 |
| DOCX | 제목 스타일을 Markdown 제목 단계로, 표를 Markdown 표로 변환. 문서 안 이미지는 EasyOCR로 글자를 읽음 |
| XLSX / XLS | 시트마다 Markdown 표 하나로 변환 |
| PPTX / PPT | LibreOffice로 PDF로 바꾼 뒤 윤준서 님의 PDF 파이프라인에 연결 |

HWP를 읽는 파이썬 라이브러리로는 pyhwp가 가장 잘 알려져 있었지만 AGPL-3.0이라 쓰지 않았습니다. 네트워크로 서비스하면 소스 전체를 공개해야 해서 상업용 사내 도구에는 맞지 않았습니다.

배포 서버에서 HWP 업로드가 계속 실패한 적이 있습니다. 처음에는 한글 파일명 인코딩을 의심했는데, 실제 원인은 리눅스용 LibreOffice에 HWP 가져오기 필터가 없다는 것이었습니다. H2Orestart 확장과 `libreoffice-java-common`을 설치해서 해결했습니다. 구형 `.xls`는 LibreOffice가 성공으로 끝나면서도 결과 파일을 만들지 않아서 xlrd로 직접 읽게 바꿨습니다.

7월 28일 파서를 Docling 하나로 합치면서 이 패키지는 정리했고, Docling이 HWP를 지원하지 않아 HWP 업로드도 이때 막았습니다. 10월에 한컴 공개 명세로 파서를 새로 짜서 다시 받게 했습니다(아래 10월 기록 참고).

### 2. 클라이언트 컨택

고객사 연구자님과 연락하는 일을 맡았습니다. 매주 진행보고서를 써서 구글 드라이브에 올리고, 이메일로 보고드린 뒤 피드백을 받았습니다. 설계에 반영한 피드백은 다음과 같습니다.

- "검색 정확도 80%"가 무슨 뜻이냐는 질문을 받고, "검색 결과 상위 5개 안에 원하는 문서가 들어오는 비율"로 정의를 고쳤습니다.
- 시스템이 최신 문서를 자동으로 골라 확정된 것처럼 보여주면 안 된다는 의견에 따라, 후보로만 제안하고 대표 문서는 사용자가 지정하게 했습니다.
- 연구자님이 제안한 문서 분류(사양서·연구자료·발표자료·보고서)를 카테고리로 그대로 썼습니다.
- 인터뷰에서 "GPU가 없다"는 말을 직접 들었고, 이것이 CPU만으로 돌아가게 만든 이유입니다.

### 3. 모델 호환성과 오픈소스 라이선스 검토

기능이 되는지와는 별개로, 이 라이브러리와 모델을 고객사 환경(폐쇄망, 상업 용도)에서 써도 되는지 확인했습니다. 기준은 인터넷 없이 동작할 것, CPU로 돌아갈 것, 상업적 이용이 자유로운 라이선스(Apache 2.0, MIT 등)일 것, 세 가지였습니다.

- pyhwp(AGPL-3.0)는 채택하지 않고 LibreOffice 방식으로 대신했습니다.
- PyMuPDF도 AGPL-3.0이라 초기 PDF 파서에서 pdfplumber로 교체됐습니다(교체 작업은 윤준서 님).
- Ghostscript도 AGPL이라 표 추출 백엔드 후보에서 7월 2일에 뺐습니다.
- LibreOffice·ClamAV처럼 GPL·MPL 계열 도구는 코드에 라이브러리로 붙이지 않고 별도 프로세스로 호출만 했습니다.
- 임베딩 모델은 다국어 MiniLM(Apache 2.0)으로 정했습니다. 한국어 질문으로 영어 문서를 찾아야 했고, 384차원이라 CPU에서도 빨랐습니다.

`requirements.txt`에 라이브러리마다 라이선스를 주석으로 달아 둔 것도 이때입니다.

### 4. 로그인과 2차 기능 (7월 20일 ~ 21일)

MVP 배포 뒤, 사내에서 쓰려면 필요한 기능을 한꺼번에 붙였습니다. Google 로그인, 관리자/일반 사용자 화면 분리, 북마크, 알림, 계정별 검색 기록, 부서별 열람 제한이 이때 들어갔고, 태블릿·모바일 폭에서 화면이 깨지는 문제도 같이 고쳤습니다.

AI 요약과 자동 분류(Ollama + Qwen2.5)도 넣었다가 하루 만에 뺐습니다. 배포 서버에 Ollama를 올리려면 서버 비용이 늘어나는데, 검색 결과에서 원본 페이지를 바로 열 수 있어서 요약이 없어도 쓰는 데 지장이 없다고 판단했습니다.

로그인을 켠 날 장애가 한 번 있었습니다. 배포 서버에 Google 클라이언트 ID를 넣자마자 사이트가 빈 화면이 됐습니다. 인증 미들웨어가 `/`만 공개 경로로 두고 있어서, 로그인 화면을 그릴 JS·CSS 파일까지 401로 막고 있었습니다. 로컬에서는 프론트(5173)와 백엔드(8000)를 따로 띄우니 드러나지 않았고, 백엔드가 정적 파일까지 서빙하는 배포 환경에서만 생긴 문제였습니다. `/assets/`를 공개 목록에 넣어서 고쳤고, 서비스가 멈춘 상태라 이때만 `main`에 바로 반영했습니다.

### 5. 관리자 화면, 운영 기능, 검색 재설계 (7월 22일 ~ 25일)

관리자 화면은 직접 써 보면서 고쳤습니다. 통계를 제목 옆에 요약해 보여주고, 파싱 실패 문서와 OCR 확인이 필요한 문서를 한 탭에 모았습니다. 카테고리를 지우기 전에는 안의 문서를 다른 카테고리로 옮기게 했고, 문서를 지울 때 사유를 남기는 삭제 보고서를 만들었습니다.

운영 쪽으로는 DB와 업로드 파일을 매일 자동 백업하고(최근 14개 보관), 업로드 직후 미러 사본을 두고, 요청 수 제한과 `robots.txt`를 넣었습니다.

검색 방식도 바꿨습니다. 원래는 "정확도/균형/의미" 3단계로 BM25와 벡터 점수를 섞었는데, "지식관리"를 검색하면 형태소 분석 때문에 "지식"만 들어간 문서가 섞여 나왔습니다. 그래서 검색을 둘로 나눴습니다. 파일명 검색은 파일명 부분 일치로 찾아 최신순으로 보여주고, 유사 검색은 임베딩 유사도로 후보를 먼저 뽑은 뒤 BM25로 그 안에서 순위만 조정합니다(RRF 결합).

이 기간에 고친 문제는 다음과 같습니다.

- 일반 사용자 화면이 관리자 전용 API를 부르고 있어서 일반 계정에서 403이 났습니다. 관리자 API를 열지 않고, 부서 권한을 지키는 일반용 API를 따로 만들었습니다.
- 같은 파일명을 다시 올리면 덮어쓰게 돼 있었는데, 사내 문서는 버전이 다르면 둘 다 남아야 해서 새 버전으로 추가하게 바꿨습니다. 고치는 중에 저장 경로가 겹쳐 기존 파일이 덮어써질 수 있는 문제도 찾아서 막았습니다.
- 화면이 8초, 20초마다 서버에 상태를 묻고 있었습니다. 사용자가 늘면 부하도 같이 늘어서, 수동 새로고침과 창으로 돌아왔을 때만 확인하게 바꿨습니다.
- 배포 DB(PostgreSQL)에서만 날짜 필터가 서버 오류를 내던 문제와, 시각이 9시간 늦게 찍히던 문제를 고쳤습니다.
- 업로드 파일 악성코드 검사(ClamAV)를 붙였다가 같은 날 되돌렸습니다. ClamAV가 시그니처 DB만으로 메모리를 800MB~1.2GB 쓰면서 OCR·임베딩 모델과 메모리를 다퉜고, 스와핑 때문에 PostgreSQL 체크포인트가 269초까지 걸리고 일부 업로드가 500 오류로 실패했습니다.

### 6. Elasticsearch·Docling 전환 (7월 28일 ~ 31일)

프로그램이 끝난 뒤의 작업입니다. 기존에는 벡터 인덱스(turbovec)를 메모리에 두고, BM25 인덱스는 검색할 때마다 새로 만들고, RRF도 직접 짜 넣은 구조였습니다. 이것을 Elasticsearch 하나로 옮겼습니다.

- BM25와 벡터 kNN을 따로 질의하고, RRF는 파이썬에서 계산합니다(벡터 k=30, BM25 k=60). Elasticsearch에도 RRF가 있지만 무료 자체 호스팅에서는 Enterprise 라이선스가 필요했습니다.
- 한국어 형태소 분석기 nori를 붙였습니다. 플러그인 설치만으로는 안 되고, 인덱스 설정에서 분석기를 직접 정의해야 했습니다.
- 배포 환경에서는 Elasticsearch에 영구 저장소를 붙일 수 없어서, 재시작으로 인덱스가 비면 DB에 남겨 둔 임베딩으로 다시 색인하는 작업이 10분마다 돌게 했습니다.
- PDF·DOCX·PPTX·XLSX 파서를 Docling 하나로 합쳤습니다. OCR 품질이 낮은 페이지는 Docling이 매기는 등급(POOR/FAIR)으로 판단합니다.

같은 시기에 저장소를 개인 저장소로 옮기고, 서비스 이름과 도메인에서 `km-platform`을 지우고, 화면마다 URL이 따로 잡히게 바꿨습니다.

## AX 이후 (2026.10)

### 10월 24일 ~ 25일: 라이선스 정리, HWP 재지원, 모델 결정

처음 정한 라이선스 기준을 다시 꺼내 의존성을 하나씩 확인했고, 기준에서 벗어난 것이 두 개 나왔습니다.

하나는 검색 엔진입니다. 쓰고 있던 Elasticsearch 8.15 이미지 안의 `LICENSE.txt`를 열어 보니 Elastic License 2.0이었습니다. 같은 역할을 하는 OpenSearch 3.9.0과 nori 플러그인(둘 다 Apache-2.0)으로 옮겼고, BM25와 벡터를 따로 찾아 RRF로 합치는 구조는 그대로 두었습니다.

다른 하나는 OCR입니다. EasyOCR가 끌어오는 python-bidi가 LGPL이었습니다. Docling이 지원하는 RapidOCR(Apache-2.0)로 바꾸면서 한국어 인식 모델을 따로 지정했는데, 바꾸고 나서야 이전 설정이 스캔본의 한국어를 한 글자도 못 읽고 있었다는 것을 알았습니다(재현율 0%). 지금은 59.5%를 읽습니다.

HWP·HWPX도 다시 받게 했습니다. 한컴이 공개한 「한글 문서 파일 형식 5.0」 명세를 보고 `backend/core/hwp_parser.py`를 직접 짰고, 외부 프로그램 없이 파이썬(olefile, lxml)만 씁니다. 가지고 있던 HWP·HWPX 35개를 모두 읽었고, 한컴이 같은 문서를 PDF로 내보낸 것과 비교하면 본문 글자의 97.8%가 일치했습니다. 빠진 것은 쪽 번호와 반복 머리말입니다.

라이선스 점검 결과 백엔드 패키지 142개 중 허용형이 아닌 것은 certifi와 tqdm(둘 다 MPL-2.0)뿐입니다. requests·huggingface_hub 같은 필수 라이브러리가 요구해서 뺄 수 없고, 수정하지 않고 쓰면 MPL-2.0은 상업적 이용을 막지 않습니다.

### 10월 25일 ~ 26일: 무료 서버를 찾다가 집 노트북에 올림

처음에는 Oracle Cloud Always Free(ARM 2 OCPU, 12GB)에 올리려고 했습니다. ARM용 이미지를 빌드해서 OCR부터 유사 검색까지 도는 것도 확인했지만, 서버 자체가 만들어지지 않았습니다. 7월에 자동 재시도를 550번 넘게 돌렸을 때도, 10월에 다시 돌렸을 때도 "out of host capacity"였습니다.

다른 무료 선택지도 맞지 않았습니다. 이 구성은 문서를 파싱할 때 메모리를 7GiB 가까이 쓰는데(앱 4.66GiB + OpenSearch 2.06GiB), AWS·GCP·Azure의 상시 무료 서버는 메모리가 1GB 수준입니다. 크레딧형 무료 체험은 몇 달 뒤 끝나고, Hugging Face Spaces 무료 CPU는 재시작할 때마다 디스크가 비워집니다.

그래서 집에 있던 여분 노트북을 서버로 쓰기로 했습니다. 설치하면서 막힌 곳이 하나 있었는데, 설치 화면에서 와이파이를 잡아도 설치가 끝나면 연결이 안 됐습니다. 설치 프로그램이 네트워크 설정 파일에 `match:` 항목을 넣는데, 서버 Ubuntu가 쓰는 networkd는 와이파이에서 이 항목을 지원하지 않아 설정 전체가 적용되지 않고 있었습니다. 그 항목을 지우고 `dhcp4`를 넣어서 해결했습니다.

### 10월 26일: 창 모드에서 잘리던 화면 정리

창을 줄여서 쓰면 화면이 깨지는 곳이 있어서, 창 폭 12가지(1920~480px)로 화면을 자동으로 찍어 보며 찾았습니다.

- 폭이 1100px보다 좁으면 상단 메뉴가 "…"로 접혀 업로드와 북마크가 안 보였습니다. 탭이 세 개뿐이라 접히지 않게 했고, 600px보다 좁을 때만 아이콘으로 줄입니다.
- 관리자 화면은 900px보다 좁으면 탭 여섯 개 중 두 개가 숨었습니다. 그 폭에서는 아이콘만 보이게 했습니다.
- 관리자 화면 1100~1260px에서는 탭이 왼쪽 로고 글자를 덮었습니다. 1280px부터 탭을 로고 옆 남는 공간에 놓게 바꿨습니다.
- 좁은 창에서 왼쪽 아래 로그인 카드가 검색창을 가렸습니다. 같은 기능이 오른쪽 위 프로필 메뉴에 있어서 좁을 때는 숨겼습니다.

### 10월 26일 ~ 27일: 알림 바로가기, 다운로드 횟수, 휴지통, 무관 결과 거르기

- 댓글 알림을 누르면 그 문서와 댓글로 바로 갑니다. 처음에는 알림 제목으로 파일명 검색을 하는 방식이었는데, 제목과 파일명이 다르면 못 찾아서 문서 번호로 바로 여는 방식으로 바꿨습니다.
- 조회수를 다운로드 횟수로 바꿨습니다. 미리보기만 해도 올라가던 숫자는 의미가 약했습니다. 파일을 실제로 받을 때만 1씩 올리고, 브라우저가 이어받기로 보내는 중간 구간 요청과 HEAD 요청은 세지 않습니다.
- 로고를 누르면 검색어가 주소창에 남아 처음 화면으로 돌아가지 않던 문제와, 빈 검색어가 최근 검색어에 쌓이던 문제를 고쳤습니다.
- 문서를 지우면 바로 없애지 않고 휴지통에 30일 동안 둡니다. 원본 파일, 파싱 결과, 검색 조각(임베딩 포함)은 휴지통 폴더로 옮기고, 문서 정보·댓글·북마크·열람 권한은 삭제 기록에 함께 저장합니다. 관리자가 삭제 보고서에서 복원하면 같은 문서 번호로 돌아오고 댓글과 북마크도 함께 돌아옵니다. 30일이 지나면 파일과 DB 기록을 모두 지웁니다. 본인이 지운 문서도 삭제 보고서에 남게 했습니다.
- 유사 검색에서 문서와 상관없는 질문(예: "김치찌개 끓이는 법")에도 결과가 10개 넘게 나왔습니다. 의미 검색은 아무리 먼 문서라도 점수를 매겨 돌려주기 때문입니다. 질문에서 조사·어미·의문사를 빼고 남은 단어의 75% 이상이 맞는 문서만 키워드 후보로 씁니다. 키워드가 맞는 문서가 없으면 의미 점수 0.74 이상인 문서만 남기고, 키워드가 맞는 문서가 있으면 거기에 의미 점수 0.78 이상인 문서만 더합니다. 기준값은 `SEARCH_BM25_MIN_MATCH`, `SEARCH_SEM_MIN_SCORE`, `SEARCH_SEM_STRONG_SCORE` 환경 변수로 바꿀 수 있습니다.

## 처음 계획한 기술 스택과 바뀐 과정

프로젝트를 시작할 때 팀이 정한 스택은 다음과 같았습니다.

- 파싱: PyMuPDF + EasyOCR(PDF) / pyhwp + LibreOffice(HWP)
- 검색: BM25(rank-bm25 + kiwipiepy) + 벡터(MiniLM) 하이브리드, Vector DB는 미정
- 백엔드/화면: FastAPI + SQLite / React
- 요약(보조): Ollama + Gemma 3 4B (포함 여부 미정)
- 전부 CPU 전용, 외부 클라우드 API 미사용
- 오픈소스는 MIT/Apache 2.0만 사용
