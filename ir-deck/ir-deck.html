Constraint → Edge

10주, GPU 없이, 사내 보안 규정 안에서
그 제약이 만든 선택들

CPU 전용 구동
GPU 없이 EasyOCR·임베딩·turbovec(16배 압축 벡터 인덱스)까지 전부 CPU만으로 처리하는 아키텍처를 구성했습니다.
파싱 동시 실행 제한
CPU 부하가 큰 파싱 작업은 한 번에 하나씩만 처리합니다. 문서가 여러 개 동시에 업로드돼도 검색·조회 같은 다른 API 응답이 느려지지 않도록 백그라운드에서 순차 처리합니다.
환경 독립 아키텍처
DATABASE_URL 하나만 바꾸면 코드 수정 없이 로컬 SQLite → Railway PostgreSQL → 사내 온프레미스로 이식 가능하게 설계했습니다.
라이선스
사용하는 모든 오픈소스는 MIT·Apache 2.0 등 상업적 이용 가능한 라이선스만 채택했습니다(AGPL 계열은 의도적으로 배제).

Wrap-up

10주, 무엇을 만들고 무엇을 배웠나

가장 크게 배운 것
예산과 리소스가 제한된 상황에서 무엇을 만들고 무엇을 포기할지 우선순위를 정하는 감각을 익혔으며, 실제로 배포하고 나서야 보이는 문제(대용량 문서 처리, 동시 접속 부하)가 있다는 걸 몸으로 경험했습니다.
가장 어려웠던 것
기획부터 백엔드·프론트엔드·배포까지 전 과정을 맡아 진행하며, 그때그때 우선순위를 스스로 판단하고 조율해야 했던 점이 가장 큰 도전이었습니다.
다시 한다면
실시간 알림(안 읽음 개수) 기능은 DB 폴링 대신 Redis 기반으로 다시 만들 것 같습니다. 휘발성이 큰 Redis는 폴링을 넣어도 서버 부담이 훨씬 적다는 걸 프로젝트를 진행하며 독학으로 배웠습니다. 예산 문제로 미뤘던 LLM 자동 카테고리·요약 기능과 ClamAV 악성 파일 검사도, 서버 메모리 비용을 감당할 방법을 더 적극적으로 찾아 지금보다 나은 결과물을 만들 수 있다고 자신합니다.
